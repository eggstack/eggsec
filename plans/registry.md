## Status vocabulary

- **proposed** — roadmap or plan exists but is not approved for execution.
- **ready** — dependencies and interfaces are satisfied; plan may be handed off.
- **active** — implementation or closure work is in progress.
- **blocked** — a named dependency or evidence requirement prevents progress.
- **closing** — implementation landed and closure evidence is being gathered.
- **closed** — closure record accepted (flat-era: inline completion record).
- **conditionally closed** — substantial work landed, but a named correctness or operational evidence condition remains.
- **superseded** — replaced by another document.
- **archived** — no longer active and retained for traceability.

### desktop-gui-frontend (M1–M3 closed 2026-10-23; M4–M5 implemented 2026-10-23; M6–M9 planned 2026-10-23)

Governed by `plans/subsystems/desktop-gui-frontend-roadmap.md` with
`plans/adrs/ADR-0007-desktop-gui-frontend-boundary.md` (accepted),
`plans/adrs/ADR-0008-operation-parameter-schema-publication.md` (accepted), and
`plans/adrs/ADR-0009-gui-shell-technology-selection.md` (**accepted 2026-10-23**).
The three foundation plans below were mutually independent and were executed in
one pass; all three are **closed**. The two product plans that follow them are
**implemented**; their closure records are owned by the closure workstream and
are not written here. The four plans after those are **planned and ready for
handoff**: M6, M8, and M9 are `capability` milestones and M7 is an `operational`
one. **M7 is gated on M6, M8, and M9 closing.** M8 and M9 are tracked in this
roadmap because M6 and M7 depend on them and no daemon subsystem roadmap
exists, even though their code surface is outside the GUI crate.

The premise recorded here, because it determines the size of everything that
follows: the engine is already frontend-neutral, and the gap is not
architecture but **discoverability**. `OperationMetadata` carries identity
and policy but no parameter structure, so every frontend hand-builds its
forms — which is most of the TUI's ~65,000 lines. Publishing a mechanically
derived schema is what converts a GUI from "hand-write 34 forms" into "one
generic form engine", and it de-brittles REST, MCP, and Python as a
side effect.

- `plans/implementation/desktop-gui-frontend/001-operation-parameter-schema-publication.md` — **closed 2026-10-23**; closure `plans/closure/desktop-gui-frontend/001-operation-parameter-schema-publication-closure.md`. The schema lives behind a `schema` feature on `eggsec-runtime` and is derived from `TaskKind` + its 30 params structs; a read-only `DescribeOperations` daemon command publishes it alongside the catalog read from `OperationMetadata`. **Two recorded deviations from the plan's wording:** (a) the plan's drift detector — "the schema's variant keys equal the set of `TaskKind::operation_id()` values" — is unachievable as written, because 30 task kinds map to 26 operation ids (the three packet kinds share `packet`, `Pipeline`/`Resume` share `pipeline`, `Wireless`/`WirelessActive` share `wireless`); the artifact is therefore keyed by **task-kind variant** with the operation id as a field, which pins the exact multiplicities instead of dropping four wire shapes. (b) The catalog is read in `eggsec-daemon-protocol` (which gained `eggsec-policy`), not in `eggsec-daemon`, so the daemon's declared dependency set stays `eggsec-runtime` + `eggsec-daemon-protocol` only per guard 16. **No `deny.toml` exception was required**: `schemars`/`schemars_derive`/`dyn-clone`/`serde_derive_internals` are MIT-or-Apache-2.0, already inside the closed allow-list (`cargo deny check licenses` → `licenses ok`). Guard 151 pins the schema off every authorization path; guard 152 pins the absence of a hand-written parameter table.
- `plans/implementation/desktop-gui-frontend/002-frontend-client-contract-extraction.md` — **closed 2026-10-23**; closure `plans/closure/desktop-gui-frontend/002-frontend-client-contract-extraction-closure.md`. The contract moved to the new frontend-neutral leaf crate `eggsec-frontend-client` (workspace: **24 crates**); `TuiRuntimeClient` → `RuntimeClient`, `DaemonClientError` is now public, and `crates/eggsec-tui/src/runtime_client/` was deleted with the TUI migrated onto the new crate (1002 TUI tests green). The `Arc<DaemonConnection>` sharing that carries runtime-event fan-out was moved verbatim — cloning the connection instead of the client would silently break event delivery. Guard 153 pins the crate free of frontend frameworks and of the engine; the crate joined the mandatory `make clippy` gate.
- `plans/implementation/desktop-gui-frontend/003-desktop-gui-surface-parity.md` — **closed 2026-10-23**; closure `plans/closure/desktop-gui-frontend/003-desktop-gui-surface-parity-closure.md`. `RuntimeSurface::DesktopGuiManual` (11 variants) and `ExecutionSurface::DesktopGuiManual` (10 variants) added, with the `runtime_bridge` converting both ways. The GUI is a **manual** surface (same `ManualPermissive` profile as the CLI and TUI manual surfaces) and reuses `manual_exposable` — **no `gui_exposable` flag and no strict GUI variant were added**. **A behavior change was required and is recorded:** the daemon's audit trail previously stamped every session-scoped event with the literal `"daemon"`, so *no* frontend was distinguishable in the persisted log; session-scoped events now record the **session's** runtime surface label (`desktop-gui-manual`, `tui-manual`, …) while session-less events keep `"daemon"`. Guard 154 pins the variant's presence, its manual classification, and both conversions.

**`ADR-0009` was ratified on 2026-10-23**: Tauri v2, pinned to the **2.11.x** line, with egui/eframe pre-sanctioned as the fallback.
