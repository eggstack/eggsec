## Deviations and notes

1. **The tree was dirty.** The build was produced with `--allow-dirty`
   because milestone 007's own documents and scripts were uncommitted and two
   other milestones were editing the tree concurrently. The sidecar records
   `tree_state: "dirty"` and `allow_dirty: true`, so the artefact is never
   mistaken for a clean-tree release build. The CI `gui-platform` job is the
   clean-tree build path.
2. **The launch was observed only through the operating system.** The window
   itself could not be observed (see above), so no screenshot of the running
   GUI is part of this evidence.
3. **No daemon was started**, so no behavioural column (Connect, Submit,
   Cancel, Render) has evidence from this run.
4. **The binary's SHA-256 is not a function of the commit alone.** A second
   run of the same command later the same day, against the then-current
   tree, produced SHA-256
   `513caadf4613b3dbb1e65d998d9e03f6c9aa4cfca7058a3470ea0dbb7c3c0fbb` — the
   same size (5 747 424 bytes), the same commit
   (`7332baeafe5391e228a0b91fec48cf68999729f1`), and the same `Cargo.lock`
   hash, but a different binary. The cause is that another milestone edited
   `crates/eggsec-runtime/src/runtime.rs`, which is in the GUI's dependency
   closure, while the tree was dirty. This is the concrete reason the build
   metadata records the **tree state** and not just the commit: on a dirty
   tree the commit SHA and the lockfile hash are both necessary but not
   sufficient to identify the artefact. The SHA-256 recorded in this file is
   the one belonging to the run documented here.
